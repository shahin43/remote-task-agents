Current positioning

The board is the control surface. The sandbox is the execution boundary.

The service is not a general chat assistant and not an agent runtime exposed to external channels. It is a durable, auditable work queue: a task is assigned, control resolves policy, a worker runs in isolation, and the result returns as a snapshot, diff, artifact, summary, and handoff.

01

Board-driven

Humans and deterministic control decide what runs. Model output never becomes routing authority by itself.

02

Session-first

Conversation and lifecycle are durable events. Every attempt remains observable and replayable.

03

Harness-owned effects

Handoffs, promotion, comments, credentials, and policy are mediated outside the model.

What happens end to end

The current proven loop is intentionally simple. New capabilities should enter through typed seams rather than weaken the control/execution split.

1Task intakeBoard task, assignee, repos, priority, creator.
2Control routingResolve registered agent, profile, skills, scope.
3Atomic claimWorker claims a routing session with ownership lease.
4Fresh sandboxDocker or unix-local workspace and task bundle.
5Agent runPi executes scoped tools against the workspace.
6CheckpointSnapshot, diff, artifacts, summary, usage.
7HandoffHarness validates intent and returns work to agent or human.

Core layers to protect

These are the service's compounding assets. Hardening them produces more value than adding use-case-specific paths.

1Harden now

Identity, authorization & tenancy

  • Server-derived actor; remove client identity headers.
  • Viewer/operator/admin roles and project membership.
  • Tenant-scoped repository methods and artifact authorization.
  • CORS, CSRF, token/session lifecycle, negative tests.
2Harden now

Durable commands & routing

  • Idempotent task creation, assignment, follow-up, approval.
  • Atomic routing and continuation under concurrency.
  • Exact profile and skill version pinning.
  • Control remains the single scheduling authority.
3Harden now

Worker ownership & recovery

  • Lease renewal/heartbeat rather than one fixed long lease.
  • Fenced completion and cleanup by lease generation.
  • Crash, timeout, cancellation, and restart reconciliation.
  • Never silently swallow a lost operational ledger update.
4Harden now

Sandbox & credential isolation

  • Provider capability contract and hostile-input tests.
  • Egress policy, secret allowlists, resource ceilings.
  • Archive/path/symlink safety and fresh-envelope precedence.
  • Docker ownership, cleanup, and multi-worker isolation.
5Strong base

Sessions, events & attempt ledger

  • Ordered event replay and pagination.
  • One indexed agent_runs row per attempt.
  • Projection repair and transactional completion.
  • Retention, indexing, and query performance at scale.
6Strong base

Snapshots, artifacts & continuity

  • Checksummed snapshot integrity and restore tests.
  • Declared, authorized artifacts rather than workspace exposure.
  • Retention with live-attempt and min-keep protection.
  • Multi-host store seam and orphan reconciliation later.
7Improve

Observability, usage & economics

  • Normalize usage at ingestion, preserve raw provider values.
  • Per-attempt, task, profile, project, and daily rollups.
  • Pricing provenance, budgets, alerts, and missing-data flags.
  • Metrics for latency, failures, leases, snapshots, and queues.
8Extend later

Interfaces & ecosystem

  • Task conversation after core command correctness.
  • Mobile control after identity and authorization.
  • Channels and notifications through explicit seams.
  • Cloud sandboxes and orchestration only after real demand.

Usage, tokens & cost

The persistence model is correctly attempt-first, but the current normalization and display path is only partially trustworthy.

Current truth

Tracked per attempt; rolled up per task.

Task totals should always be derived from immutable attempt records—not maintained as an independent mutable counter.

What existsagent_runs.token_usage is saved on finalization. Attempts are linked to task id and attempt number. The API returns attempt rows and a task rollup; the drawer displays task totals and a compact attempt token indicator.
What is unreliable todayThe Pi engine emits inputTokens/outputTokens/cache*, while rollup/display code looks mainly for input/output or provider names. Pi cost is not retained in the usage contract. Real totals may therefore show zero and cost commonly remains unknown.
LevelCurrent stateRecommended hardening
Provider turnInput/output and cache counters are aggregated in the Pi loop.Normalize once at ingestion; include provider, model, request id, and explicit completeness.
AttemptRaw JSON usage persists on the agent_runs row.Add typed normalized fields: input, output, cache read/write, cost micros, currency, pricing version.
Task/api/tasks/:id/usage sums attempts at read time.Keep derived rollup; show a table by attempt/agent/model with missing-cost markers.
Project / tenantNo product dashboard or durable aggregate.Add date/profile/model/status rollups after tenant authorization exists.
BudgetsCycle and runtime caps exist; token/cost enforcement does not.Admission and stop policies using trusted normalized usage, with audit events.
Recommended rule: preserve the raw provider usage JSON for diagnostics, but make every UI, budget, and report consume one canonical normalized attempt-usage contract. Record “unknown” rather than silently treating missing cost as zero.

Hardening backlog

Filter the list to separate the immediate reliability spine from product improvements and later extensions.

R-01P0

Make attempt finalization durable

Usage, artifacts, summary, and snapshot references cannot remain best-effort writes. Add retry/reconciliation and alert on incomplete terminal rows.

R-02P0

Normalize usage correctly

Unify engine output and rollup field names, retain provider cost, test real runner shapes, and display unknown values honestly.

R-03P0

Atomic/idempotent commands

Concurrency-test assignment, routing, follow-up, handoff, completion, approval, and retry commands.

R-04P0

Lease heartbeat & fencing

Renew ownership during long runs; reject stale completion; prove worker death, network loss, and duplicate reconciler behavior.

R-05P0

Identity and authorization

Server-derived users, roles, project membership, artifact access, CORS/CSRF, and tenant-negative tests before mobile/shared use.

R-06P1

Immutable execution envelope

Pin profile/model/skills/scope at route time; verify restored work cannot expand authority or replace runtime configuration.

R-07P1

Snapshot integrity at scale

Corruption, partial writes, orphan cleanup, retention races, disk pressure, and multi-host storage parity.

R-08P1

Operator observability

Queue depth, attempt latency, sandbox startup, failure taxonomy, profile success rate, usage/cost, and reconciler health.

R-09P1

Clean split-topology proof

Run API, control, worker, and reconciler separately; verify restarts, concurrency, credentials, readiness, and shutdown.

R-10P2

Task conversation MVP

Render existing session history and attempts as a conversation; avoid coupling it to token streaming or orchestration.

R-11Later

Mobile control surface

Authenticated task queries and confirmed commands, foreground invalidation, and background push notifications.

R-12Later

Provider & orchestration ecosystem

Cloud sandboxes, project assistant, and autonomous coordination only through proven seams and validated demand.

Pragmatic extension path

Grow from a trustworthy local core toward mobile and community extensibility without turning the next phase into a platform rewrite.

Now

Reliability spine

Correct usage accounting, durable completion, command idempotency, lease heartbeats, immutable profiles, snapshot integrity, and split-process evidence.

Next

Task conversation, kept small

A better view over existing task/session history and safe follow-up. Polling or lightweight invalidation is sufficient initially.

Then

Access layer and mobile-ready commands

Server identity, roles, authorized task/artifact APIs, confirmed assignment and approval commands, plus notification seams.

Later

Project assistant

Read-only project status and natural-language proposals converted into typed commands that require human confirmation.

Validated demand

Autonomous orchestration and cloud providers

Separate runtimes, child sessions, budgets, and hosted sandboxes only after real workflows justify their operational cost.

Definition of robust: a clean checkout can run the split topology; concurrent commands are idempotent; crashed workers reconcile without duplicate effects; every attempt has a complete or explicitly incomplete ledger; unauthorized cross-project access fails; snapshots restore safely; and live Docker/provider gates prove the same contracts used by unit tests.
