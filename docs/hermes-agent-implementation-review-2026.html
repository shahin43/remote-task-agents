How Hermes remembers, delegates, and coordinates.

A source-grounded architecture review of Hermes Agent’s profile identity, memory hydration, self-learning, subagent delegation, durable work handoff, hosted agent discussions, and session continuity.

Executive conclusion

Not one agent bus—four bounded protocols.

Hermes keeps identity and durable knowledge profile-local, then uses different protocols for different jobs: a curated memory store for stable facts, isolated subagents for bounded delegation, Kanban for durable work ownership and handoff, and hosted rooms for bounded conversational exchange. This separation avoids forcing chat, work state, and long-term memory into one overloaded session abstraction.

The operating model

Hermes is a personal agent runtime with multiple surfaces. The narrow waist is the agent loop plus profile-scoped state; CLI, gateway, TUI, desktop, cron, Bot Mode, Kanban, and hosted rooms adapt around it.

Profile island

Config, credentials, memories, skills, sessions, gateway state, and agent personality live under one resolved HERMES_HOME. A profile does not live-inherit changes from the default profile.

Conversation runtime

AIAgent owns model turns, tool execution, compression, persistence, and external-memory hooks. The system prompt is kept stable to preserve provider prefix caching.

Work coordination

Delegation serves one parent turn; Kanban serves durable multi-profile work; hosted rooms serve conversational multi-agent discussions. Their state machines are intentionally different.

Durable stores

state.db stores sessions and usage. Each Kanban board has its own SQLite database. Hosted-room identity, events, leases, tasks, replicas, and link receipts are durable gateway state.

Memory is layered, bounded, and profile-owned

Hermes treats “memory” as three separate retrieval tiers: always-present curated facts, on-demand transcript search, and an optional external semantic/provider layer. None of these are the child subagent transcript.

Curated profile memory

Tier 3

External provider

At most one external memory plugin is active. It can supply a static prompt block, prefetch turn-relevant context, sync completed turns, react to boundaries, expose tools, and observe delegated results.

Write correctness

  • Cross-process file locks serialize mutations.
  • Files are re-read under lock before writes.
  • Unreadable files fail closed instead of being overwritten.
  • External drift blocks replace/remove operations.
  • Batch mutations validate fully and commit atomically.
  • Exact duplicates are idempotent.
  • Prompt-injection, exfiltration, and invisible-Unicode patterns are scanned.

Hydration and cache correctness

  • Built-in memory is immutable within a conversation prefix.
  • External recall is fenced into the API-bound user turn rather than mutating the system prompt.
  • The exact API-side content is persisted separately for byte-stable replay.
  • Trivial prompts skip semantic recall.
  • A deterministic UI indicator reports when recall was actually injected.
  • Compression can require a provider checkpoint before discarding raw context.
Association model: the built-in memories are associated with a profile, not with an individual session or subagent. External providers receive profile identity, session identity, platform, workspace, and optional user/chat/thread coordinates, so a provider may implement finer-grained namespaces. Hermes itself guarantees only the profile home and lifecycle metadata it passes.

“Learning” means curation, not model training

Hermes does not fine-tune an agent over time. It turns durable signals into two editable assets: compact facts in memory and reusable procedures in skills.

Continuous

Foreground memory tool

The main agent can proactively add, replace, remove, or batch-consolidate facts. A failed capacity check returns current entries and asks the agent to consolidate in the same turn.

Periodic

Background review fork

After configured turn intervals, an isolated review agent replays the conversation and may update memory or skills. It shares the parent’s built-in stores but skips external memory providers, limiting accidental double-ingestion.

Explicit

/learn and skill curation

/learn converts a described workflow or source into a profile skill. Usage telemetry then drives deterministic stale/archive transitions; optional LLM consolidation is off by default.

Delegation: orchestrator → child

  1. The parent requests one task or a batch. Runtime configuration—not the model—sets child iteration, concurrency, and depth limits.
  2. The child inherits only capabilities the parent has; memory, clarify, Kanban, and other role-blocked tools are removed. Delegation is re-added only while depth permits.
  3. The child gets a dedicated SessionDB connection pointing to the same profile database and a parent_session_id link.
  4. Foreground execution waits. Top-level detached execution can continue in the background and later re-enter a routable session; finite one-shot contexts fall back to synchronous execution.
  5. Finalization applies summary budgets, emits lifecycle events, notifies memory providers at the parent, and closes child resources.

Hosted rooms: agent ↔ agent

  1. A user event opens a thread against a frozen roster of 2–6 local or peer members.
  2. Round one targets explicit mentions, or everyone when there are none. Later rounds are opt-in: only newly mentioned peers respond.
  3. Each member receives only the unseen, bounded transcript delta and explicit privacy/pass rules.
  4. Task and turn IDs are deterministic hashes of the room, event, member, round, watermark, and prompt.
  5. A reply is published before its terminal receipt; replay ignores uncommitted visible messages so a crash can finish publication idempotently.
  6. The loop settles on silence or stops after three rounds / ten member messages.
The strongest design decision:

Hermes does not use conversational messages as work ownership. Hosted-room messages are append-only discussion events; Kanban transitions are authoritative work state. Likewise, a delegation summary is context returned to a parent, not a board handoff. This prevents prose from silently changing durable responsibility.

Session continuity and identity

SQLite sessions are the durable transcript spine. Compression, branches, delegates, gateway routes, Bot Mode, and usage all hang from explicit session identities rather than a single mutable chat blob.

SessionDB

WAL-backed SQLite with FTS5, jittered write retries, longer patience for transcript-critical writes, system-prompt deduplication, model-route usage, turn leases, and maintenance bounds.

Compression lineage

Compression ends one session and creates a child continuation through parent_session_id. Locks, watermarks, publish transactions, and lineage-aware reads prevent stale writers and preserve the logical conversation.

hermes_state.py:8440+, 10964+, 12428+

Bot Mode

Each Bot profile owns a canonical forever conversation resolved by the exact hidden title Bot Chat. The name is the registry identity; there is no separately stored pointer. Side chats remain separate sessions.

hermes_state.py:10271–10453

Profile scoping

get_hermes_home() resolves a context-local override before the process environment, allowing a multiplex gateway to route concurrent requests into different profile homes. Context variables are copied into memory background workers so writes keep the correct scope.

Usage association

Main and auxiliary model calls are accumulated per session and coherent provider/model route. Background review records its cost back to the parent under an auxiliary task label. This is operational accounting, separate from memory.

Architecture assessment

Hermes is strongest when it uses explicit state machines and weakest where best-effort background work can be mistaken for a durability guarantee.

A−

Strong implementation with carefully bounded autonomy

The source shows mature attention to profile isolation, prompt-cache stability, SQLite contention, replay, idempotency, capability reduction, stale work, and hostile content. The deduction is for several intentionally best-effort or process-bound paths that adopters must not reinterpret as durable orchestration.

Patterns worth retaining
  • Profile as the durable identity and knowledge boundary.
  • Frozen prompt memory plus explicit next-session hydration.
  • Session search instead of unbounded prompt memory.
  • Provider lifecycle behind one narrow interface.
  • Depth-derived delegation capability and strict child tool reduction.
  • Dedicated child DB handles and explicit parent lineage.
  • Board state—not chat—as work ownership.
  • Append-only events, deterministic IDs, authority epochs, and replayable room policy.
  • Hard conversational bounds and an explicit pass protocol.
  • Learning split into editable facts, procedures, and usage telemetry.
Constraints to carry forward
  • Built-in file memory assumes one active agent writer per profile home; documentation warns against shared-home multi-agent use.
  • External memory sync/prefetch is best effort; shutdown waits are bounded and may abandon provider work.
  • Detached delegation needs a live routable host session; finite contexts correctly fall back to synchronous work.
  • Delegate children intentionally have no independent memory; any desired child learning must be promoted through the parent.
  • Kanban’s tenant field is a namespace, not a security boundary; the board/database is the hard boundary.
  • Hosted rooms are a separate, comparatively large protocol surface: authority, grants, peer transport, replicas, leases, policy, and recovery all need to travel together.
  • The canonical Bot Chat title is a deliberate magic registry key and must remain protected by title/update invariants.
  • Recalled external memory is prompt context and remains untrusted data even when useful; provider provenance and poisoning controls matter.
Adoption sequence implied by Hermes itself: establish profile identity and session durability first; add bounded built-in memory and search; then isolated delegation; then durable task handoff; only after those invariants are solid, add multi-agent rooms and external memory providers. Hosted discussion is not a prerequisite for reliable agent work.
